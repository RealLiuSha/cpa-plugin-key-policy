# cpa-key-policy

`cpa-key-policy` is a CLIProxyAPI plugin, shown as 萝卜 ("Luobo") in the CPA management panel. It issues downstream keys, prices upstream models with a per-model multiplier, bills usage and enforces RPM and USD limits; it also tracks success rate, latency and list-price spend per channel (CPA credential), rewrites request bodies per channel, can move Codex web search onto each channel's own web_search tool (native search) with alpha search as the fallback, and tests credentials with the candy, fingerprint, ModelTrace and pelican tests for a degraded or substituted model. The plugin ID, the config key and every management path stay `cpa-key-policy`. Exhausted quotas and RPM answer with HTTP 429, every enabled key may use every model CPA serves, and a model without a price bills $0 and is flagged until a price is set. This release targets Linux x64 on Debian 12 / glibc 2.36 or newer and writes data format 7. See [release and upgrade instructions](RELEASE.md).

## Model prices

The model layer is a price table. A `ModelPrice` row prices one upstream model id (`name`, the `Model` CPA reports in usage records, compared without case) with an optional `provider` qualifier, the billing mode (`tokens` or `per_call`), the prices and the billing multiplier. The same `(name, provider)` pair exists once. Lookup prefers the row matching `(provider, model)` and falls back to the row with an empty provider; CPA's `openai-compatible-<name>` provider keys are compared by `<name>`.

There are no public model names, no routing and no per-key model lists. CPA routes every request by its own registry: when a model is served by several providers, CPA chooses credentials across them and fails over; the response carries whatever model upstream reports. Any enabled key may call any model and may always read the model lists `/v1/models`, `/openai/v1/models` and `/v1beta/models`: listing counts neither RPM nor quota and works while a quota is used up. Gemini generation routes under `/v1beta/models/<model>:…` are admitted like any other call.

A call is unpriced when no row matches, when a token row has every price at 0, or when a per-call row has `per_call_usd` 0. Unpriced calls bill $0; their tokens and calls are still recorded and each is counted in `unpriced_calls`. `GET /models` lists under `unpriced` the models whose calls in the last 90 days matched no row and that still have no row for any provider; `has_qualified_rows: true` marks a model whose rows are all provider-qualified, so calls from other providers missed them (check the qualifier or add a row without one). An all-zero row is flagged in the price table itself (`priced: false`). The `priced` flag of `GET /keys/usage` and `GET /stats` model rows is the ledger's: every call shown was charged; a model without calls falls back to its row. Token prices are USD per million tokens between 0 and 10000, `per_call_usd` between 0 and 10000, `billing_multiplier` between 1 and 50 (default 1).

## Configuration

See [`config.example.yaml`](config.example.yaml). The current shape is:

```yaml
enabled: true
state_file: cpa-key-policy-state.json
usage_timezone: Asia/Shanghai
search_enabled: false
cpa_config_path: config.yaml

models:
  - name: gpt-5.6
    provider: codex
    billing_mode: tokens
    input_price_per_million: 1
    output_price_per_million: 2
    cache_read_price_per_million: 0.1
    cache_write_price_per_million: 0.3
    billing_multiplier: 1.1

keys:
  - id: team-a
    enabled: true
    key_hash: sha256:replace-with-hash
    rpm: 60
    daily_limit_usd: 10
    weekly_limit_usd: 50
    monthly_limit_usd: 150
```

Two keys belong to the plugin itself:

- `search_enabled` (default false): when true the plugin takes over Codex web search: it registers a response interceptor that rewrites the Codex model catalog for the models whose channels passed a check (native search), and a model router that chooses the model for `POST /v1/alpha/search` for the models that fall back. Both are set up on the Search page. While false neither is registered, so ordinary requests do not cross into the plugin once more. The response interceptor follows `search_enabled`, not the native search switch on the page: while it is registered CPA hands every successful non-streaming response, with its request, to the plugin, which reads only the first fields (about 0.2 µs), but encoding the crossing costs CPA about 30 µs for a 20 KB chat, 3.5 ms for a 2 MB compaction and 32 ms with 255 MB of allocations for a 20 MB image edit, most of it the crossing itself. Keep `search_enabled` off on an instance that serves large non-streaming requests.
- `cpa_config_path` (default `config.yaml`, relative to CPA's working directory): read only for detection, to list the config's API keys under the IDs CPA gives them, for an adapter rule's real try, for the group names on the Channels page, and to tell whether a channel can be deleted. The key is used in process and never written to a file, a log line or an API response.

The first boot seeds keys and price rows from YAML and creates a state file and a usage file with the same `dataset_id`. After that, the state file is authoritative for keys and prices; YAML only controls `enabled`, `state_file`, `usage_timezone` and the two keys above. CPA resends the configuration on every config apply; when the block did not change the plugin does nothing and does not reread its data files, so editing those files while the plugin runs needs a restart to take effect. The exception is a build that already ran in this CPA process and is registered again after it gave the data directory up (CPA reuses the plugin image still loaded, as when `store.version` switches back to it or the plugin is re-enabled after another build ran): it reloads the files and replays the handoff journal instead of serving what it kept in memory, and fails registration when they do not load. When CPA discards such a load and rolls back to the instance it replaced, that instance serves on, bills every record once and can start detection tests again.

At registration an unknown top-level key only adds a warning (shown on the Settings page) instead of failing registration. Once data is loaded, a configuration that cannot be applied is rejected and the last valid one stays in effect, also reported on the Settings page; a changed `usage_timezone` is refused at once, without rereading the files. A first start that cannot load its data still fails registration. `cpa-key-policy-check --config` stays strict: settings of earlier releases (`target_model`, `targets`, `dispatch`, `free`, `group`, `classify_rules`, `keys[].models`, `keys[].allow_models_endpoint`, `keys[].limits_changed_at`) and any other unknown key fail it; check a configuration with it before switching.

Channels, adapter rules and search settings each keep a file next to the state file: `cpa-key-policy-adapters.json`, `cpa-key-policy-search.json`, `cpa-key-policy-search-native.json` (native search settings and check results), `cpa-key-policy-channels.json` and `cpa-key-policy-channel-stats.json`, the detection history in `cpa-key-policy-quality.json`, and the daily inspection's settings and results in `cpa-key-policy-inspection.json`. They are not part of the v7 dataset; an older release ignores them, so a rollback can leave them in place. Channel statistics are written every 5 minutes and exactly at shutdown and hot replacement, so a crash loses at most 5 minutes of them, never billing. `scripts/publish.py` backs these files up together with a handoff journal no instance replayed yet. Releases 0.16.0 and earlier parse the configuration block strictly, though: remove `search_enabled` and `cpa_config_path` from `plugins.configs.cpa-key-policy` before rolling back, or registration fails and every key gets 401. They do not replay the handoff journal either, so roll back to them by restarting CPA, never by switching `store.version` in a running CPA ([RELEASE.md](RELEASE.md) has the rules). Two seed keys sharing one secret are rejected on first boot. Startup strictly rejects an unsupported file version, a missing pair, a mismatched dataset, a usage file written for another timezone and a history watermark (`through`) later than today in `usage_timezone`.

## Accounting

Amounts are integer nanodollars inside the ledger (1 USD = 1e9), so totals are exact and deterministic; the management API reports USD as floats and configuration keeps USD prices and limits. The ledger holds one bucket per key, model and natural day for the last 90 days (`calls, unpriced_calls, input_tokens, cache_read_tokens, cache_write_tokens, output_tokens, charged_nano, cache_read_cost_nano, cache_write_cost_nano`) plus each key's three quota cycles; day totals are computed from the model buckets when read. Three files share one `dataset_id`:

- `<state_file>` (indented JSON, `version` 7): keys and price rows.
- `cpa-key-policy-usage.json` (compact JSON): every key's quota cycles, a balance key's `balance` (`balance_nano`, `net_credited_nano` and the remembered request ids) and the days newer than `history_through`. It is rewritten whole every 15 seconds while dirty.
- `cpa-key-policy-history.json` (compact JSON): the closed days up to `through` inside retention. It is rewritten on the first flush after midnight and again when retention drops a day; a closed day is never rewritten otherwise. For 1000 keys this takes about 100–300 ms, blocks only the flusher goroutine and never holds the ledger lock.

Snapshots are taken under the ledger lock and serialized outside it; a failed write keeps the data dirty, is retried on the next tick and is visible in `/status` as `health.last_flush_error`. While the ledger stays unsaved the Overview page warns too (a `usage ledger not saved …` line in the `warnings` of `GET /overview`), and CPA's log gets one line when saving first fails and one when it succeeds again; the failures in between go to stderr only. Unloading the plugin writes a final cut, history first; an instance that no longer holds the data directory, such as one replaced by a hot replacement, writes nothing. CPA shuts its plugins down before it stops its usage queue, so the last few usage records still queued when CPA stops never reach the plugin and are not billed. A live file that names a history day but has no history file, a mismatched `dataset_id`, a foreign timezone or a negative counter refuses startup rather than repairing the ledger. A record whose date falls on a closed day, after the clock was turned back, is booked on the first open day, so closed history never changes. Deleting a key removes its cycles and RPM window at once and writes the live file immediately (a failed write is logged and left to the flusher); its history stays until it expires and is reported as deleted in statistics.

Each key has independent daily, 7-day and 30-day quota cycles under `cycles`. Daily quotas reset at 00:00 in `usage_timezone` (default `Asia/Shanghai`). Where daylight saving time starts at midnight (America/Santiago or Africa/Cairo, for example) the switch day has no 00:00, so that day, and any 7-day or 30-day deadline on it, starts at its first instant, 01:00; every other day starts at 00:00, and zones without such a day, Asia/Shanghai and UTC among them, are unaffected. Earlier releases could put that boundary at 23:00 of the day before; a usage file they wrote in such a zone is refused at startup until its cycles are corrected. The 7-day and 30-day cycles are fixed calendar-day periods anchored at the key's creation: the first deadline is the creation day plus 7 or 30 days at 00:00, automatic advancement continues from the original deadline across idle periods and downtime, and a manual reset restores only the selected cycle and sets its next deadline to the operation day plus 1/7/30 days at 00:00. Other cycles and history are preserved. Changing limits, enabled state or a key secret does not reset consumption. A manual reset writes the live file under the ledger lock so the file holds exactly one accounting cut (about 10–25 ms at 1000 keys); this is deliberate and is revisited when a reset exceeds 50 ms.

A key has one of two quota types, `quota_mode`. `cycle`, the default, is limited by the daily, 7-day and 30-day quotas described above. `balance` is prepaid: it has no period limits, and its only limit is a balance that administrators adjust with `POST /keys/balance` (a positive `amount_usd` adds credit, a negative one deducts). Every billed call of a balance key is deducted from its balance in the same lock that books its cycles, and the key is refused once the balance is 0 or below; since billing follows a call, calls in flight when the balance ran out can leave it slightly negative. An adjustment is written to the live file before it is answered and recorded as an `adjust_balance` audit event with the amount, the balance before and after, the note and the request id; deductions are flushed every 15 seconds with the rest of the ledger, so a crash loses at most the last 15 seconds of deductions. A `request_id` makes a retried adjustment return its first result (`duplicate: true`) instead of adjusting twice; the last 64 ids per key are kept, and the same id with another amount is refused with 409 `request_id_conflict`. Switching a key to `balance` clears its period limits, and a balance key given period limits is refused; switching back to `cycle` keeps the balance unspent until the key is switched to `balance` again. Deleting a key drops its balance, which the `delete_key` audit event names. The cycles keep counting for balance keys and drive their usage page and statistics.

`usage.cycles` exposes the start, reset date, reset kind, used amount, limit and manual-reset preview date. `usage.status` is `normal`, `warning`, `limited` or `disabled`; `blocked_reason` names the exhausted cycle, or `balance_exhausted`. `usage.quota_mode` repeats the key's quota type; `balance_usd` and `net_credited_usd` (the signed sum of all adjustments) appear for balance keys and for a cycle key that kept a balance, and a balance key is `warning` once 80% of its net credit is spent. `daily_usd`, `weekly_usd` and `monthly_usd` are the current cycle charges. History charts use `/keys/history`. `next_accounting_boundary_at` equals the daily cycle's `resets_at`.

Billing happens once, when CPA delivers the usage record of a finished call:

- A record with `Failed` set is never billed. This includes streams the client cancelled, which CPA records as failed with status 499: their partial tokens are not charged.
- A record in which a field billing does not read (`BaseURL`, `AuthID`, `AuthIndex`, `RequestedAt`, `Latency`, `TTFT`, `Failure`) changed its type is billed without that field; a type change in a field billing reads, `Detail` included, leaves the record unbilled. Either is logged at most once a minute.
- The key is matched by id, then by plaintext hash. It need not still be enabled: the request was authorized when it started.
- The model is the upstream `Model`; the requested name is used only when that is empty. Bucket keys are the lowercased id, so per-model totals never split by the case upstream reported.
- Negative token counts become 0. An input, output, reasoning, cache-read or cache-write count above 2^31 rejects the whole record (`invalid_usage`); an out-of-range `total_tokens` or `cached_tokens` is only set to 0, since neither is billed. A record that needed either correction counts once in `clamped_tokens`.
- A token record with no billable tokens after classification (input, cache read, cache write and output all 0) is ignored when its model is priced (`ignored_empty_usage`). When the model is unpriced it is recorded as one call with `unpriced_calls` 1, so a new model whose records carry no tokens still shows up as unpriced; a video model without a `per_call` row therefore also counts every result poll as a call until it is priced.
- Token classes follow CPA's own accounting per provider. For Claude and Anthropic providers cache reads and writes are outside the input count; for Gemini, AI Studio, Vertex, Antigravity and interactions the reasoning tokens are outside the output count; everyone else reports cache reads inside the input and reasoning inside the output. Cache reads come only from `CacheReadTokens`. A zero cache-read price bills reads at the input price; without a cache-write price, cache writes are billed as input. Input, output, cache-read and cache-write charges all use the multiplier; token counts stay real. Each of the four classes is rounded to a nanodollar on its own and the charge is their sum, so the cache amounts shown separately never exceed it. Changing a price or multiplier affects later calls only.
- A `per_call` row bills once per admitted media generation request. The request interceptor remembers the trace id of each admitted POST on the image and video generation routes CPA intercepts (`/v1/images/generations`, `/v1/images/edits`, `/v1/videos`, `/v1/videos/generations`, `/v1/videos/edits`, `/v1/videos/extensions`, `/openai/v1/videos`; 4096 entries, 1 hour), and the usage record that carries the same trace id is charged `per_call_usd`. Every other record of a per-call model is left unmetered (`unmetered_per_call`): result polling, an expired trace, a host without trace ids, a media route CPA does not intercept (such as `/openai/v1/images/*`), and the image model record that a Codex `image_generation` tool call on `/v1/responses` adds. Price models that report tokens, such as Codex's `gpt-image-*`, by token. Losing a trace makes one call free, never double-billed.

`GET /status` exposes `health`: `last_flush_at`, `last_flush_error`, `flush_failures`, `skipped_failed`, `ignored_unknown_key`, `ignored_no_model`, `ignored_empty_usage`, `clamped_tokens`, `invalid_usage`, `unmetered_per_call` and `unpriced_calls`. The counters live in memory and start at zero on every start.

## Request rejection

| Situation | Where | Client sees |
| --- | --- | --- |
| Unknown or disabled key, plugin disabled | Authentication | 401 (CPA's generic answer) |
| Key only in the query string on an image or video generation route, or on a WebSocket handshake (`GET /v1/responses`, `GET /backend-api/codex/responses`) | Authentication | 401 |
| RPM limit reached | Request interceptor | 429 `rate_limit_exceeded`, `Retry-After` = seconds left in the one-minute window |
| Prepaid balance used up (balance keys) | Request interceptor | 429 `insufficient_quota` on every OpenAI-style route including the Responses API, without `Retry-After`: a balance never resets on its own |
| Daily, 7-day or 30-day quota used up | Request interceptor | 429 `insufficient_quota`, `Retry-After` = seconds until the latest exhausted cycle resets; on the Responses API `type` is `usage_limit_reached` with `resets_at` (Unix seconds) so Codex shows the reset time, and `code` stays `insufficient_quota` |
| Model lists (`/v1/models`, `/openai/v1/models`, `/v1beta/models`) | Authentication | Always allowed for an enabled key, without RPM or quota |

Admission checks RPM first, then the quotas, and names the exhausted cycle that resets last. CPA turns any frontend-auth rejection into 401, while its request interceptor can terminate a request with any status before contacting upstream (CPA v7.2.103 and later). Requests are admitted in the interceptor when the key is sent in a header and the route is one CPA intercepts with an HTTP answer: chat/completions, completions, responses, messages, count_tokens, images, videos (generation and retrieval), speech and TTS (`/v1/audio/speech` and `/v1/tts`, which CPA has from v8.0.18), `/v1beta/models/*`, interactions and the codex responses routes. Everything else is admitted during authentication with the 401 behavior: keys passed in the query string, realtime, live and alpha/search routes, and WebSocket handshakes on `/v1/responses` and `/backend-api/codex/responses` (a rejected WebSocket turn only closes the socket, so a handshake with the key in a header checks quota and the interceptor counts RPM per turn). A key sent only in the query string is refused on a media generation route, because the interceptor cannot see it and per-call billing depends on the trace id the interceptor records. It is refused on a WebSocket handshake too: each turn is admitted by the interceptor, which gets the handshake's headers but no query string, so such a key would be checked once and never again. Browser WebSocket clients cannot set headers and are refused; Codex sends the key in a header.

The 429 body follows the caller's protocol: OpenAI-style `{"error":{"message","type","code"}}`, Claude-style `{"type":"error","error":{"type":"rate_limit_error","message"}}`, or Gemini-style `{"error":{"code":429,"message","status":"RESOURCE_EXHAUSTED"}}`. Messages name the exhausted limit and when it resets in `usage_timezone`. Retrieving an already generated video is never blocked by quota.

CPA skips a request interceptor that returns an error, so a plugin fault lets that one request through; it is still billed by `usage.handle`. Keep at least one undistributed key in CPA's `access.api-keys`: if the plugin fails to load or is disabled, CPA then rejects every request instead of serving them unauthenticated.

## Management API and Web UI

The panel shows one 萝卜 menu with these pages: Overview, Keys, Channels, Models and prices, Stats, Search, Quality, Audit and Settings. Inside the CPA management panel it shows only its section tabs; opened on its own it adds the endpoint and a sign-out button. The page carries an ETag, compared weakly (`W/"…"` and `*` match too), so the reload the panel does on every menu click is a 304 check. A client that accepts gzip gets a copy compressed once, under the ETag `"<sha>-gz"`; every answer carries `Vary: Accept-Encoding`, the SHA the Settings page shows is the plain page's, and a proxy in front that clears `Accept-Encoding` gets the plain page. When `cpa-key-policy-ui/index.html` exists in the data directory the plugin serves it instead of the embedded page, so a UI update does not need a new plugin library. The management base path is:

```text
/v0/management/plugins/cpa-key-policy
```

`GET /keys` items carry `id, name, enabled, key_preview, rpm, daily_limit_usd, weekly_limit_usd, monthly_limit_usd, quota_mode, usage, created_at, updated_at`. `key_preview` keeps the first 7 and last 5 characters of a key of 24 characters or more, the first 3 and last 2 of a shorter one and only `...` for 8 characters or fewer; it is set when a key is created, rotated or changed, so earlier previews keep their form. `POST /keys` and `PATCH /keys` accept `quota_mode` (`cycle` or `balance`), and a PATCH that switches to `balance` clears the period limits it does not set. `POST /keys/balance` answers `{id, amount_usd, balance_before_usd, balance_usd, net_credited_usd, duplicate}`; it refuses an amount of 0 or beyond ±1,000,000 and a note over 200 characters with 400 `invalid_amount`, a cycle key with 409 `not_balance_mode` and an unknown key with 404. `POST /keys` and `PATCH /keys` reject unknown fields but accept and ignore `models` and `allow_models_endpoint`, which earlier releases had, so existing writers keep working. A secret already used by another key is refused with 409 `duplicate_key` on create, update and rotate. `DELETE /models` answers 404 `not_found` for a row that does not exist. A management write whose state file cannot be written answers 500 `persist_failed` and leaves the running policy unchanged.

`GET /keys/usage` lists the models seen in the key's current cycles with `billing_mode`, `billing_multiplier`, `priced` and the `daily`, `weekly` and `monthly` windows. `GET /stats` returns at most 200 keys ordered by charge and sets `keys_truncated` with `keys_total` when more exist; it also lists `unpriced_models`. The CSV export has the columns `date,key_id,key_name,deleted,model,calls,unpriced_calls,input_tokens,cache_read_tokens,cache_write_tokens,output_tokens,charged_usd`, prints amounts as exact decimals and prefixes cells starting with `=`, `+`, `-` or `@` with a quote. A range over the limit answers 413 `range_too_large`.

Quota reset accepts an optional `expected: {started_at, reset_after_manual_at}` alongside `id` and `window`. The ledger checks the preview under its mutation lock and returns `409 quota_changed` if the period or proposed deadline changed. The UI refreshes and requires another confirmation; existing clients without `expected` retain the original request contract.

Price import never creates rows. It applies token prices to every row whose model id matches, regardless of provider qualifier, and keeps the multiplier.

A channel is one CPA credential, identified by CPA's `auth_index`: for an API key credential from config.yaml it derives from the type, base URL and key, so proxy, prefix and header edits keep it; an OAuth credential uses its auth file's `auth_index`. Channel statistics come only from CPA's usage records, one per upstream attempt including attempts that failed over to another credential, so they need no probe requests. A Codex `image_generation` tool call adds a second, successful record for the same attempt (same credential, trace id and request time, the image model): its tokens and cost are added, but it is not another attempt and adds no latency sample. A record without a trace id or request time always counts as an attempt. A client cancel that lands before the upstream answers, including any cancel of a non-stream request, is recorded by CPA as failed with status 499; channel statistics ignore it, since it says nothing about the upstream. A cancel after the stream started produces no record, and neither does alpha search. The list cost of a per-call model counts one `per_call_usd` for the generation request billed per call and nothing for its other records. The statistics of a channel without settings from `PATCH /channels` are freed once it has been idle for the whole 7-day window; `DELETE /channels` (the Delete button of a channel CPA no longer lists) forgets one at once. Releases 0.21.0 and earlier also kept a cost ratio and a balance source per channel; those fields are ignored on load and dropped at the next write. CPA exposes no cooldown state for API key credentials from config.yaml, so the channel page shows their configured state (such as `excluded-models: ["*"]`) and their recent failure rate.

Native search: Codex decides how to search from the model catalog CPA serves. A Responses Lite model (`use_responses_lite`) is sent no hosted tool and can only call `/v1/alpha/search`, which few upstreams implement; any other model declares the `web_search` tool with the conversation, and the channel serving the turn runs it. Through host callbacks the plugin pins a short request with the `web_search` tool to each codex channel to check whether it really searches: once per channel per round, taking turns among the models it serves, a full round every interval (12 hours by default), a new channel at once and a failing one hourly; every check is a real, paid search request. A channel keeps its last 6 results: all searched is supported, some is unstable, none is unsupported, two failures in a row is failing, and no newer passing check for two rounds and an hour is outdated. Once one channel serving a catalog model is supported (or, with `require_all`, every serving channel that is not disabled), the plugin turns Responses Lite off for it in the catalog and Codex switches to native search within about five minutes; without such a channel the model stays on alpha search. Which models a key serves comes from its `models` in config.yaml (the client name first, and with the key's `prefix` also the prefixed name, alone under `force-model-prefix`, as CPA registers them); a credential that lists none is confirmed by checks. The search runs on the channel serving the conversation and cannot be moved: sessions on a channel without support do not search, and the page lists those channels per model. For a channel the operator disabled, or that refused the tool (a client request that failed with 400, 404 or 422 naming `web_search`), the plugin takes the tool out of the requests sent to it in `request.intercept_after`, together with the `web_search_call` items the history replays, for which CPA would declare the tool again; a refusal is checked again after 10 minutes and holds until a check searches. Hidden models such as `codex-auto-review` are left alone.

Rewrite rules run after CPA picked the credential and before its executor translates the request (`request.intercept_after`), apply to that attempt only and write the client's format; only requests a rule matches have their body decoded. CPA's own payload rules can neither match a credential nor move a field, so upstream quirks of this kind belong here.

From 0.25.0 channel statistics are also kept by model: the model the client asked for (the upstream one when there is none), without a reasoning suffix such as `(high)` and in lower case, as CPA's model lists name it; a channel hour breaks down by at most 16 models, and further ones count only for the channel. Each model keeps attempts, failures and status codes, and its tokens read the way billing reads them (`policy.ShapeTokens`: prompt tokens include cache reads and writes, generated tokens include reasoning), which give the cache hit rate (cache reads over prompt tokens), the reasoning tokens per successful attempt, the visible output speed after the first token (reasoning left out: CPA marks the first token at the first event with content, and Codex streams no reasoning, so its reasoning time falls before the first token) and the mean first-token time (both over successful streamed attempts that reported a first-token time: a non-stream response arrives whole, so its first-token time is about its latency; the usage record's `Stream` field tells them apart). With a model chosen, the channel page compares the channels serving it: those with at least 20 successful attempts in the last 24 hours take part, and reasoning tokens, cache hits or output speed under 60% of the model's median are marked Low (not compared when the median is too small: under 50 reasoning tokens, under 10% cache hits). It all comes from real traffic, with no extra upstream request; the plugin's own detection and inspection requests carry no downstream key and count only among the channel's attempts, not in the per-model statistics; clients' own reasoning efforts and routing priorities move the numbers, so it is a hint for the page, not an overview finding. The channel detail lists its 7 days by model, each model linking to its comparison. Statistics files of older releases have no per-model part, so it builds up from the upgrade; an older release ignores it on rollback and drops it at its next write.

Detection was refactored from cpa-codex-candy-eval, which no longer needs to be installed. Credentials come from two places: the auth files of CPA's auth manager, and the API keys of the config.yaml that `cpa_config_path` names (shown only as a mask and their group name). The credential list CPA gives plugins leaves the config's API keys out, so the plugin derives their credential IDs from config.yaml by CPA's rules; when the config cannot be read the page says so and auth files can still be tested. Each request goes through CPA pinned to the chosen credential, and CPA translates the protocol. Every candy, ModelTrace and pelican request carries the full Codex CLI context of a new session, about 14k input tokens; the quick, standard and strict fingerprint modes send 60, 200 and 400 short requests per credential. They are real upstream calls: they count as attempts in the channel statistics but bill no downstream key, and starting a test and clearing records are audited (`run_quality`, `clear_quality`, with the test as target). A credential runs one test at a time and keeps the latest 20 records of each test made in the last 90 days; candy and pelican requests share 16 slots across all credentials (`max_parallel` in the test parameters), a model stream over 16 MB is cut off and recorded as an error without a retry, and a fault while calling CPA fails only that request. The history is written at most 5 seconds after a test records and at once on shutdown, hot replacement and clearing, so a crash loses at most those 5 seconds. When the history file cannot be read, saving pauses and the page says so; clearing all records (`DELETE /quality/results?test=all`) sets the file aside as `<file>.corrupt-<UTC time>` and saving resumes. When the data directory holds candy-eval's `cpa-codex-candy-eval-state.json` and no `cpa-key-policy-quality.json` yet, the first start reads its history once; a candy-eval file that cannot be read is only not imported. A hot replacement cancels running tests and waits up to 15 seconds for them: CPA cannot cut short a request it is still opening, since a model stream can be closed only once `execute_stream` answered, and the per-request timeouts do not cover that wait either. Tests still running after that close their own streams and save nothing. At shutdown CPA refuses the plugin's callbacks, stream close included, before it calls the plugin, so a cancelled test ends only when its upstream sends again; the final billing cut and the channel statistics are written before that wait. Fingerprint normalization skips Unicode NFC composition (so as not to add golang.org/x/text); it is the only computational difference from candy-eval, and model answers are normally NFC already.

## Third-party components

The daily inspection (the Inspection page) asks chosen channels the candy question at fixed times, with no external scheduler. Channels are grouped by model: a group is a model with a reasoning effort and channels (kept by auth_index). At each time every channel is asked the configured number of questions one after another, channels in parallel within the 16 slots the manual tests use; the default is 08:00, 14:00 and 20:00 in the plugin's `usage_timezone`, three questions each, off until enabled. A day's answers add up per channel and model: at least two thirds right is OK, at least one third suspect, fewer degraded, and no answer at all failed; a channel CPA no longer has, disabled or cooling down is skipped. Channels judged degraded or suspect over the last 24 hours are listed among the overview's channels to look at. The plugin checks the schedule every minute and runs it only on the instance holding the data directory; a missed time (CPA down, or a hot replacement cancelling the round under way) catches up with today's latest time only, never an earlier one. A finished round is written to `cpa-key-policy-inspection.json` at once; results are kept for 90 days and wrong answers for 14, apart from the 20 records of the manual tests. When that file cannot be read the schedule pauses, and saving the inspection settings sets the file aside as `<file>.corrupt-<UTC time>` and resumes it. Changing the settings is audited as `update_inspection` and starting a round by hand as `start_inspection`, both with `inspection` as target; scheduled rounds are not audited. From 0.25.0 every round asks new variants: flavors, shapes, item name, column order and counts (4–12) are random, the answer is computed by the shape-first solution (`candyAnswer`, checked in tests against every possible draw) and is at least 4 below the answers of the usual mistakes (drawing blind, securing one pair); the question ends asking for a line "答案：<number>", and the judge reads the number after the last 答案, else the last number. Every channel of a round gets the same questions, so the results compare; the questions are kept in the round with the wrong answers. Each day each group also has a best of group: when two or more channels answered and even the best is not OK, the group is low (the model or the effort likely cannot do the question) and the overview lists one group finding instead of each channel as degraded. The manual candy test keeps the published question. The page picks channels from CPA's model lists (`/v0/management/auth-files/models`: the names clients ask for, with excluded models and provider defaults applied): a new group starts with every channel serving the model checked, and those left unchecked are remembered as ignored. The groups then follow CPA by themselves: each round also asks every other enabled channel the group does not ignore, which costs nothing for a channel without the model (CPA answers `auth_not_found` at once, without an upstream request); channels that answer join the group, members CPA no longer serves the model from (recorded once as skipped `not_serving`) or no longer has (skipped `missing`) leave it, and the change goes to CPA's log. A channel cooling down or disabled keeps its place. When no channel serves a group's model in a round, as while CPA reloads its credentials, the members stay. So a channel that starts serving the model is inspected from the next round unless it is ticked off in the group, and the page's notice about new channels is only a chance to ignore them first.

## Upgrading data

The plugin reads data format 7 only and refuses any other version at start. A format 6 dataset (0.11.x) is converted offline, while the instance is stopped, into a new set of format 7 files; `scripts/publish.py` does it during its maintenance window, and by hand it is:

```bash
go run ./cmd/cpa-key-policy-check --state /path/to/cpa-key-policy-state.json --timezone Asia/Shanghai --out /path/to/new-empty-dir
```

The source files are only read. The tool writes state, live usage and history into the output directory and compares them with the source (dataset id, every key's identity and limits, the price rows projected from the models, every retained bucket's counters and amounts, every quota cycle's interval, kind and consumption); it then starts and restarts the plugin's store on a private copy to prove the files load and a restart changes nothing, so the output stays exactly as converted. A source that would not convert or load is refused before anything is written. Without `--out` it rehearses the conversion in a private directory; on a format 7 dataset it only loads and reloads.

The conversion keeps keys, key hashes, limits, quota cycles and history inside retention; it drops each key's model list, model list switch and per-model daily limits, projects every model onto a price row keyed by its upstream id (`target_model`; when several public names pointed at one upstream model, the name equal to the upstream id wins, otherwise the first in lexical order, and the rest are dropped), converts amounts to nanodollars and drops the redundant day totals after checking them against the model buckets. The report lists what was dropped or chosen under `removed_settings` (ignored per-key model authorizations, removed per-model daily limits, keys that had `/v1/models` disabled, renamed and dropped price rows, recomputed day totals, keys sharing one secret), models whose public name differed from the upstream id under `renamed_models`, the counts under `conversion`, and `policy_sha256`, a normalized hash of keys and prices that must be identical before and after the start.

To install the result, move the old state file, its usage file and any `.before-v*.json` recovery files out of the state directory (keep them with the backup) and move the three new files in; the audit log stays. Older plugins cannot read format 7: roll back by restoring the backup taken before the switch. The prepaid balance fields (`quota_mode` in state, `balance` in the live file) are written only once a key uses them, so releases before them still read a dataset in which no key ever became a balance key; after that, rolling back to such a release also needs the backup. See [RELEASE.md](RELEASE.md).

`go run ./cmd/cpa-key-policy-check --config /path/to/config.yaml` checks that this release accepts the `cpa-key-policy` section of a CPA configuration, since a rejected section fails registration.

## Security and operational notes

- Store only hashes in configuration or state; generated plaintext keys are returned once.
- State, usage and history files may contain operationally sensitive metadata and must remain owner-readable only.
- Management audit events record semantic mutations and never a secret or hash. A failed audit append is logged but does not roll back a successful state mutation.
- Credential selection and token parsing retain CPA behavior; the plugin registers a model router and a response interceptor only while `search_enabled` is true: the router answers alpha search requests only, and the interceptor rewrites only the Codex model catalog (any other non-streaming response passes at the first member naming a model).
- Request bodies are read in place from the host's memory for the duration of a call, and decoding skips the base64 body, so even tens-of-megabytes Codex requests only add the host's own copy.
- Before a hot replacement CPA sends `plugin.quiesce`: the plugin writes its data once more and from then on only appends billed records and channel statistics attempts to the handoff journal `cpa-key-policy-handoff.jsonl`, which the newer instance replays, so both hand over record by record, until CPA rolls the replacement back with a new configuration. A replayed record is booked on the day it was billed, or the first open day when that day is closed, and only in the quota cycles that had started by then. Quiesce waits at most 15 seconds for running detection tests, and management writes wait meanwhile. An instance that cannot take the data directory back after a rollback stays read-only: its management writes answer 503 `upgrading` with a message saying so, until the lock is free and CPA applies its configuration again.
